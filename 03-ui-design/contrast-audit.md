# 对比度核算

> 阶段 3 · 2026-11-13 · 基准：[design-system.md](design-system.md) v1.1 的对比度条款
> 核算对象：`src/styles/global.css` 的实际 token 与构建产物在浏览器中的真实渲染
> 结论：**首轮发现 6 类未达标项，修正后全部通过**。修改面为「新增 1 个 token + 4 处声明 + 1 处构建配置」，
> 没有改动任何既有颜色 token 的色值。

## 结论

- 文档里写明的对比度要求可以归为三条：正文 4.5:1、大号展示文字 3:1、UI 边框 3:1；另有
  "`--ink-faint` 在 `--bg` 上 ≥ 4.5:1"与"暗色边框约 1.56:1 保证可见"两条具名指标。
- 第一次按 token 取值逐对计算（亮/暗各 40 余项）时，有 6 类不达标：
  1. 主按钮悬停用纯白字，在暗色强调色上只有 **2.76:1**；
  2. 所有可交互控件（筛选胶囊、搜索框、分享、标签胶囊、输入框）的边框用 `--rule`，只有 **1.36 / 1.56:1**；
  3. 浅色主题下订阅色带内的焦点环是深蓝 `--focus`，在墨色底上只有 **2.88:1**；
  4. 订阅色带占位符（45% 前景）只有 **4.16 / 3.67:1**；
  5. 代码块语法着色来自 Shiki 的 `vitesse-dark`，最低 token 只有 **2.35 / 2.34:1**；
  6. 装饰性分隔线（区块线、色带内分隔线、色带外框）按字面 "UI 边框 ≥ 3:1" 判定全线不达标。
- 处理原则是"能改使用方式就不改 token"：第 1、3、4 项改用法，第 2 项新增专用 token，
  第 5 项换高对比主题，第 6 项修正判定口径（装饰线不属于 WCAG 1.4.11 的对象）。
- 复测：token 级 81 项全部通过；真实渲染复核 4 个页面 × 2 主题共 90 项全部通过
  （另有 12 项因表单未渲染记为缺失，见第 8 节）。
  最小余量出现在「链接压在 `--accent-wash` 上」（浅色 4.65，+0.15）与「色带占位符」（深色 4.78，+0.28）。

## 1. 判定基准

| 文档条款 | 出处 | 目标 | 本次判定范围 |
| --- | --- | --- | --- |
| 背景上的文字 ≥ 4.5:1 | §2 规则 | 4.5 | 所有正文、次要文字、元数据、按钮/胶囊文字、色带内所有文字、代码块文字 |
| `--ink-faint` 在 `bg` 上 ≥ 4.5:1 | §2 token 表 | 4.5 | `--ink-faint` 在 `--bg` 与 `--bg-raised` 上分别计算 |
| 正文 ≥ 4.5:1，大号展示 ≥ 3:1 | §8 | 4.5 / 3 | 本站所有展示字号实测都 ≥ 14:1，统一按 4.5 判，不利用大字号豁免 |
| UI 边框相对相邻颜色 ≥ 3:1 | §8 | 3 | **仅**可交互控件的边界（输入框、胶囊、搜索、分享、标签）与焦点指示；装饰性分隔线不在此列 |
| 焦点在两种主题下都有足够对比 | §2 token 表 | 3 | 焦点环相对实际相邻底色（含色带内、强调底色上） |
| 暗色边框约 1.56:1，保证发丝线可见 | §9 | 视觉可见 | 装饰线按 ≥ 1.3:1 判定（低于此值在屏幕上会消失） |
| 不使用纯白文字 | §9 | — | 所有前景色检查是否为 `#fff`；代码块由 Shiki 提供的前景色单独复核 |

口径修订说明：v1.1 原文把"UI 边框 ≥ 3:1"写成一条普适规则，但同一份文档的 §2 与 §9 又要求
发丝线保持克制（暗色 `--rule` 只有 1.56:1）。两者只能同时成立的前提是把 3:1 限定在
**承担识别功能的边界**上。WCAG 1.4.11 的对象也是"识别控件所必需的视觉信息"，纯装饰分隔线不在其中。
本次按此口径执行，并在 design-system v1.2 中同步了措辞（见第 6 节）。

## 2. 方法

- 公式：WCAG 2.2 相对亮度 `L = Σ c·f(v)`，`f(v)=v/12.92 (v≤0.04045) 或 ((v+0.055)/1.055)^2.4`，
  对比度 `(L1+0.05)/(L2+0.05)`。
- **取数一（token 级）**：把两套 token 的实际十六进制值代入公式，逐对计算；
  半透明前景（`color-mix(in srgb, var(--band-ink) 72%, transparent)` 等）先按 sRGB 空间与底色合成再算。
- **取数二（真实渲染）**：对生产构建启动 `npm run preview`，用 Chrome headless + DevTools Protocol
  在 1440px 视口、浅/暗两个主题下读取 `getComputedStyle`：文字色与祖先背景逐层合成（兼容
  Chrome 对 `color-mix` 输出的 `color(srgb …)` 格式与 alpha），边框取实际边框色，焦点取
  `outline` 与父级底色。测量期间注入 `*{transition:none}` 消除 320ms 主题过渡造成的取色污染，
  `:hover` 用 `CSS.forcePseudoState` 强制触发。
- 采样页面：`/`、`/blog`、`/blog/typescript-narrowing`（含代码块与 TOC）、`/newsletter`。

## 3. 首轮未通过项与处理

| # | 问题 | 亮色实测 | 暗色实测 | 目标 | 差额 | 处理方式 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 主按钮悬停 `color:#fff` + `--accent` | 5.98 通过 | **2.76** | 4.5 | −1.74 | 改用法：文字改用 `var(--bg)` |
| 2 | 控件边框用 `--rule`（胶囊/输入/搜索/分享/标签） | **1.36** | **1.56** | 3 | −1.64 / −1.44 | 新增 token `--control-border` |
| 3 | 色带内焦点环 `--focus` 深蓝压在墨色上 | **2.88** | 7.81 通过 | 3 | −0.12 | 改用法：色带内 `outline-color: var(--band-ink)` |
| 4 | 色带占位符 `band-ink 45%` | **4.16** | **3.67** | 4.5 | −0.34 / −0.83 | 改用法：45% → 55% |
| 5 | Shiki `vitesse-dark` 最低语法 token | **2.35** | **2.34** | 4.5 | −2.15 / −2.16 | 改用法：主题换 `github-dark-high-contrast` |
| 6 | 装饰线按字面 3:1 判定 | 1.36 / 1.52 | 1.56 / 1.32 / 1.91 | 3 | 全线 | 改口径：装饰线按 ≥1.3 可见性判定 |

第 1–5 项是真缺陷：前四项在真实页面上可复现，第 5 项影响所有带语言标记的代码块。
第 6 项不是配色缺陷，而是文档把两类边框混成了一条规则；若强行把分隔线提到 3:1，
编辑体的"发丝线"特征会被抹掉，属于为指标破坏设计方向，因此选择修正规则而不是修正颜色。

为什么第 2 项新增 token 而不是把 `--rule` 整体调深：`--rule` 同时承担区块分隔、列表行分隔、
色带内分隔等纯装饰职责，调深会让整页线条变粗、变吵，正是上一轮 UI 收敛要消除的"凌乱感"。
把职责拆成"装饰线"与"控件边界"两个 token，既满足 1.4.11，又不动编辑体的视觉基调。
控件边框从 1.36:1 变成 3.44:1 是可感知的变化（这正是缺陷所在），但仍是 1px 细线，
视觉重量远低于 `--ink` 描边。

## 8. 未覆盖与限制

- **订阅输入框未渲染**：端点为空时页面用 mailto 兜底，因此色带输入框与订阅页表单的边框、
  占位符、错误文本只能按 token 核算，未做渲染复核。接入真实端点后需要再跑一次本流程。
- **代码高亮 token**：只抽样了 `typescript-narrowing` 一篇（106 个文本节点）。该篇覆盖了
  关键字、字符串、数字、函数名、注释、标点等主要 token 类型；若以后新增语言或改主题，应重跑。
- **页头半透明**：页头是 92% 不透明度的 `--bg` 叠 `backdrop-filter`，按"下方为最暗内容"的
  最坏情况合成后计算（浅色 7.32、深色 7.46），实际滚动时不会更低。
- **点阵纹理**：`body` 上 4px 间距、1px 大小、4.5% 不透明度的点阵，对局部像素亮度的影响
  远小于 1%，不改变任何判定；但它是硬编码的 `rgba()`，不属于 token。
- **代码块背景**：Shiki 会输出内联 `background-color`，被 `--code-bg !important` 覆盖，
  因此实测底色是 `#1B1916` / `#0B0A09`；正文色实测来自主题（`#F0F3F6`），CSS 里的
  `#eee8db` 只在非 Shiki 处理的 `<pre>` 上生效。
- 打印样式（`#000` on `#fff`）、OG 卡片、Pagefind 自带 UI 不在本次范围；三者都不使用
  站内 token 体系，若需要应单独审计。
