# 分析与增长

> 阶段 7 · v1.0 · 原则：不装追踪脚本，用搜索控制台、订阅关系与真实对话衡量影响力

## 1. 为什么不装分析工具

站点在 About 页公开承诺"no trackers, no cookie wall, no algorithmic feed"。这不是姿态，而是产品定义的一部分：

- 技术层面：无第三方脚本 → 无额外网络请求、无 CSP 例外、无 cookie 同意条、无 CLS 风险。
- 读者层面：文章页只有文字，加载完成即结束，不会在后台继续上传行为数据。
- 运营层面：没有"转化漏斗"可优化，注意力回到写作本身。

代价是拿不到 UV、停留时长、跳出率。对一个以长文为主的个人博客，这些数字本来也无法说明文章是否被认真读过。

## 2. 采用的信号

| 信号 | 工具 | 能回答什么 | 成本 |
| --- | --- | --- | --- |
| 搜索曝光与点击 | Google Search Console | 哪些问题带来自然流量、标题是否吸引点击 | 免费 |
| 收录覆盖率 | Search Console | 新文章是否被索引、是否有抓取错误 | 免费 |
| Bing 索引 | Bing Webmaster Tools | 补充 Bing/ChatGPT 检索来源 | 免费 |
| RSS 订阅数 | Feed 服务商（可选） | 核心读者规模 | 免费档够用 |
| Newsletter 订阅与回复 | 邮件服务商 | 真实读者留存与反馈质量 | 免费档够用 |
| 引用与提及 | 手工搜索、邮件 | 文章是否被讨论、被链接 | 时间 |
| 服务端/CDN 日志 | 托管平台（若提供） | 状态码分布、热门路径 | 免费 |

以上均为聚合数据或读者主动行为，不涉及个体追踪。

## 3. 上线首月的搜索动作

1. 在 Search Console 添加资源，验证方式选 DNS TXT（与域名商同处管理）。
2. 提交 `https://<domain>/sitemap-index.xml`。
3. 对首页、`/blog`、3 篇精选文章使用"网址检查 → 请求编入索引"。
4. 在 Bing Webmaster Tools 导入 Search Console 资源（一键迁移）。
5. 两周后检查"网页"报告：已编入索引数应接近 22，若明显偏低，查看"已发现但未编入索引"的原因。

## 4. 关键词与标题策略

不追热点词，围绕"工程师会真的搜的问题"写作：

| 类型 | 示例查询 | 对应文章 |
| --- | --- | --- |
| 问题型 | why is my API slow | Slow APIs |
| 决策型 | monolith vs microservices migration | Rewriting the Monolith |
| 排错型 | how to find layout shift causes | CLS in Practice |
| 概念型 | typescript type narrowing explained | TypeScript Narrowing |

写作规则：

- 标题包含具体名词（`CLS`、`monolith`、`pipeline`），不用"思考""漫谈""浅析"这类空词。
- 第一段 40 词内给出结论，便于摘要与搜索片段。
- 每个 H2 是一个可独立回答的问题，便于被检索系统切成片段引用。
- description 写成人话，不堆关键词。

## 5. 增长路径（按优先级）

1. **RSS 优先**：完整全文输出，是所有聚合器与 Newsletter 的基础。任何改动不得削减 RSS 内容。
2. **Newsletter**：双周同步，作为唯一"会主动回来"的渠道。订阅动机写在 `/newsletter` 页，不设弹窗。
3. **单点分发**：发布后一天在 X / LinkedIn 发一条基于结论的短帖，不写钩子标题。
4. **被引用**：文章中的表格、清单、决策树是别人愿意链接的资产，优先做这类可复用结构。
5. **不被搜索绑架**：不为了排名拆分成多篇薄文，一篇文章只回答一个问题。

## 6. 90 天目标（现实版）

| 指标 | 30 天 | 90 天 |
| --- | --- | --- |
| 被收录文章 | ≥ 15 | 22（全部） |
| 自然搜索点击/周 | 10–30 | 50–150 |
| RSS 订阅 | 5–20 | 30–80 |
| Newsletter 订阅 | 0–10 | 20–50 |
| 收到真实回复/引用 | 1 | 3 |

这些数字对个人博客是合理区间。若 90 天后自然点击仍接近 0，先检查收录与标题，而不是加追踪脚本。

## 7. 何时才考虑加分析

满足以下全部条件时可以重新评估（但仍优先无 cookie 方案，如服务端日志聚合或 Plausible 自托管）：

1. 已有 ≥ 20 篇稳定内容；
2. 有明确的、需要数据回答的问题（例如"教程类与观点类哪类更值得写"）；
3. 能接受在隐私页明确披露并保持无横幅。

在此之前，加分析只会增加维护面，不改变决策。
