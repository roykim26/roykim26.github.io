# 长期维护

> 阶段 7 · v1.0 · 目标：一年后这个站点仍然能在 3 分钟内重新构建成功

## 1. 维护节奏

| 周期 | 事项 | 预计耗时 |
| --- | --- | --- |
| 每次发布 | 五项门禁 + 冒烟 | 5 分钟 |
| 每月 | 依赖补丁更新、外链抽查、Search Console 查看 | 30 分钟 |
| 每季度 | Lighthouse 复测、内容勘误、标签体系收敛 | 1 小时 |
| 每半年 | 从零构建演练、字体/依赖大版本评估 | 2 小时 |
| 每年 | 设计微调、文章归档整理、备份校验 | 半天 |

## 2. 依赖策略

- **Astro**：跟随小版本（`5.x`），大版本升级单独开分支，升级后跑完整门禁 + 浏览器抽查。
- **Pagefind / Sharp**：仅在构建期使用，升级风险低，但需确认 CLI 参数未变。
- **不加新依赖**：任何新依赖必须解决一个现有依赖无法解决的问题，并说明体积成本。当前运行时依赖仅 4 个（astro、rss、sitemap、marked）。
- 升级流程：

```bash
npm outdated
npm update            # 小版本
npm run check && npm run build && npm run test:links && npm run test:seo
npm run preview -- --port 4321   # 浏览器抽查首页 / 文章页 / 暗色
```

主版本升级（如 Astro 6）额外检查：`content.config.ts` 的 loader 与 schema、`build.format` 行为、Pagefind 集成方式、RSS API 变更。

## 3. 内容维护

| 问题 | 处理 |
| --- | --- |
| 文章结论过时 | 在文首加一行 `Updated <date>:` 说明改了什么，保留原文观点，不静默改写历史 |
| 代码示例失效 | 更新代码块并在 frontmatter 提升 `updatedDate`（若启用），不新发一篇文章 |
| 链接失效 | 优先换成同类一手来源；找不到就删掉链接而非保留死链 |
| 标签膨胀 | 标签控制在 6–8 个；新标签必须能聚合 ≥ 3 篇，否则复用已有标签 |
| 长文拆分 | 超过 2,500 词时考虑拆成系列，用统一前缀命名并在文首互链 |

## 4. 备份与可恢复性

内容即仓库，恢复路径极短：

1. 代码与文章：GitHub 仓库（主）+ 本地 clone（备）。
2. 构建产物：CI 每次构建上传 `site-dist` artifact（保留 7 天）；如需长期留存，可在发布时打 git tag（`v1.0.0`、`v2026.11.10`）。
3. 字体与 OG 图：字体已入库；OG 图每次构建重新生成，无需备份。
4. 配置：域名、DNS、托管账号信息记录在密码管理器中，不写入仓库。

恢复演练（每半年）：

```bash
git clone <repo> /tmp/blog-restore && cd /tmp/blog-restore
npm ci && npm run build && npm run test:links && npm run test:seo
```

四条命令全绿即视为可恢复。

## 5. 已知技术债

| 项 | 影响 | 计划 |
| --- | --- | --- |
| Google Fonts 已改为自托管，但仅含 latin 子集 | 非拉丁字符回退到系统字体 | 可接受，站点为英文 |
| Newsreader 可变字体约 132 KB | 首次访问字体下载偏大 | 可考虑子集化（fonttools）后再降 40–60% |
| 无自动化视觉回归 | 设计改动靠人工核对 | 改动频率低，暂不引入 |
| Lighthouse 未进 CI | 性能回退需人工发现 | 每季度复测一次 |
| 订阅端点未接入 | 表单降级为邮件 | 由运营者按需接入 |
| 仅英文 | 无法服务中文读者 | 明确不在 v1 范围 |

## 6. 安全与合规

- 无用户输入落库、无账号体系，攻击面仅为静态文件与 DNS。
- CSP 已收紧到 `'self'`（字体自托管后不再需要第三方源）。
- 依赖漏洞：`npm audit` 每月跑一次；构建期依赖的漏洞不影响线上运行，但仍应升级。
- 隐私：不设 cookie、不装追踪；Newsletter 若接入第三方，需在其页面说明数据由谁保存。
- 版权：文章与 OG 图版权归作者；代码示例默认 MIT，可在文末注明。

## 7. 升级到"更大"的站点时

当出现以下需求时，才考虑架构变化：

| 需求 | 现在的做法 | 触发升级的信号 |
| --- | --- | --- |
| 评论 | 邮件回复 | 每月收到 ≥ 10 条希望公开讨论的反馈 |
| 多语言 | 仅英文 | 有稳定的非英文读者群 |
| 全文搜索增强（按标签过滤、排序） | Pagefind 默认索引 | 文章 > 100 篇且搜索 CTR 明显 |
| 付费内容 | 无 | 明确不为 v1 目标 |

任何升级都必须保持"纯静态可部署"这一底线，否则会失去当前最低的运维成本。
